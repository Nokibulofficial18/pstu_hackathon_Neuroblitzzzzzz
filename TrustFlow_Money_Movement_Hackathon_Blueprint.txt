PROPOSED IMPROVEMENT
3. Final Product Vision and Scope
3.1 Product positioning
TrustFlow is a trust-first community wallet for simulated peer-to-peer money movement. It keeps the 
original challenge scope, then adds a small number of innovations that directly improve safety, 
explainability and demo value.
Product pillar Meaning
Move Send money safely to another registered user.
Request Collect money through requests, including optional partial 
payments.
Protect Prevent duplicate deductions, overspending and 
concurrency bugs.
Explain Show exactly what happened, when, why and how the 
balance changed.
Prove Use Trust Lab to demonstrate failure resistance live.
3.2 Scope boundaries
 No real bank / card / MFS / payment gateway integration.
 No attempt to replicate the entire feature set of bKash, Nagad or a bank.
 No unnecessary microservices during the hackathon; use a modular monolith.
 No “AI fraud detection” claim without a real dataset and trained model.
 Every optional feature is lower priority than transaction correctness.

REQUIRED CORE FLOWS
5. Core User Journeys
5.1 Send Money
1. Choose or search a registered receiver.
2. Show receiver identity card so the sender can verify the person.
3. Enter amount and optional purpose.
4. Validate amount, receiver, balance and duplicate request key.
5. Run risk rules; activate Safe Send only when needed.
6. Confirm the transaction.
7. Execute debit + credit atomically.
8. Show Trust Receipt with transaction ID and new balance.
Hasan balance: BDT 100,000
Send BDT 2,500 -> Saif
Result:
  Hasan = BDT 97,500
  Saif  = BDT 102,500
  Ledger difference = BDT 0
5.2 Request Money
9. Requester selects payer and amount.
10. Optional purpose / note is attached.
11. Payer receives a pending request.
12. Payer can Accept, Reject or (proposed) Pay Partially.
13. On payment, the same Payment Engine executes the financial transfer.
14. Request status updates and both users receive history entries.
5.3 Registration and starting funds
The challenge explicitly allows automatically funding each newly registered user with BDT 100,000 in 
simulated money. Treat that event as controlled system issuance rather than user-to-user transfer, so later 
system-total checks remain explainable.
CORE ENGINEERING
6. Financial Correctness Engine
Golden rule
A transfer must be all-or-nothing, one-time, balance-safe and traceable.
6.1 Atomicity
Sender debit and receiver credit happen inside the same database transaction. If any step fails, the entire 
operation rolls back.
--- PAGE 7 ---
PSTU IT Carnival 2026 | TrustFlow Solution Blueprint  •  7
BEGIN
  lock sender account
  validate balance
  create transaction
  debit sender
  credit receiver
  create ledger entries
COMMIT
If any step fails -> ROLLBACK
6.2 Idempotency / Duplicate Payment Shield
Every send request carries an idempotency_key. If the same key arrives again because of double-click or 
network retry, the backend returns the already-created result instead of charging again.
6.3 Concurrent spend protection
If BDT 1,000 is available and BDT 700 + BDT 700 are requested simultaneously, only one may succeed. Use a 
DB transaction with row locking or an equivalent serializable update so the second request sees the 
updated balance.
6.4 Balanced ledger
For every user-to-user transfer, total ledger delta must equal zero. This gives the team a simple invariant to 
test and a powerful explanation to judges.

6.5 Money conservation check
User-to-user transfer invariant:
SUM(all debits + all credits) = 0
System integrity check:
Issued simulated funds - current wallet funds - reserved/held funds = 0

PROPOSED TECHNICAL DESIGN
10. System Architecture
 Frontend handles user interaction only; it never directly changes balances.
 Payment Engine is the only module allowed to perform balance-changing operations.
 Request / Collect module creates obligations, but uses Payment Engine when money actually moves.
 Risk module produces warnings / confirmation rules; it does not bypass financial correctness.
 Ledger module writes immutable financial entries for completed transfers.
 PostgreSQL provides ACID transactions, constraints, locking and indexed querying.

REQUIRED REAL-WORLD THINKING
13. Failure Scenarios and Expected Behavior
Scenario Naive failure TrustFlow expected behavior
Double-click Send Two transfers happen. Same idempotency key -> exactly one 
financial effect.
Response lost after success User retries and pays twice. Retry returns original transaction 
result.
Two simultaneous sends Both see old balance and overspend. Account lock / atomic update allows 
only valid spend.
Server error after debit Money disappears before receiver 
credit.
DB rollback restores original state.
Negative / zero amount Corrupt or nonsensical transaction. Reject before any DB mutation.
Self-transfer Meaningless ledger movement. Reject.
Unknown receiver Money could be misdirected. Reject and show receiver-not-found.
Insufficient balance Balance becomes negative. Reject atomically.
Repeated request acceptance Same request paid more than once. State + idempotency prevent second 
payment.
History query at scale Slow dashboard. Indexed, paginated retrieval by 
account + created_at.
PROPOSED TRUST CONTROLS
14. Security and Trust Controls
 Hash passwords using a standard adaptive password hash (e.g., bcrypt / Argon2).
 Use authenticated sessions or signed access tokens; never trust user_id supplied by the client.
 Authorize every request: a user can only act on their own wallet / requests unless explicitly permitted.
--- PAGE 14 ---
PSTU IT Carnival 2026 | TrustFlow Solution Blueprint  •  14
 Validate all money amounts on the backend; frontend validation is only convenience.
 Use parameterized queries / ORM to prevent injection.
 Rate-limit login and sensitive transaction endpoints if time permits.
 Do not expose full emails or sensitive data in receiver identity cards.
 Log security-relevant events separately from user-visible transaction history.
 Never allow a normal API to directly set arbitrary account balances.

PRESENTATION PREPARATION
19. Judge Q&A Preparation
Likely question Strong short answer
What is innovative? Safe Send + Trust Lab on top of a failure-safe payment 
engine. We prove reliability instead of only claiming it.
How do you prevent double payment? Each logical request has a unique idempotency key; retries 
return the original result.
What if two transfers happen at once? Balance check and deduction run inside one DB transaction 
with account locking / atomic update.
--- PAGE 17 ---
PSTU IT Carnival 2026 | TrustFlow Solution Blueprint  •  17
What if server fails after deducting? Debit and credit are in the same database transaction, so 
failure rolls back both.
Why a ledger if you already have balance? Balance is fast state; ledger is the immutable explanation 
and reconciliation source for every movement.
Why not microservices? Nine-hour scope. A modular monolith is simpler, safer to 
integrate and still cleanly separates financial logic.
Where is AI? AI is not necessary for the core problem. We use explainable 
rules; optional NLP can create a draft request but never 
execute money without confirmation.
How will it scale? Stateless API, indexed/paginated transaction access and 
PostgreSQL first; services/partitioning only when real load 
requires them.
Is this real money? No. The challenge explicitly allows a closed simulated money 
ecosystem.
